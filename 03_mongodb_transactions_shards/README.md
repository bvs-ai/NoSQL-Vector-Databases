# Лекція 3. Практика: реплікація, транзакції, шардування

Інтернет-магазин на MongoDB 7.0 у Docker. Три частини одного заняття:

1. **Replica set з трьох вузлів**: write concern, «вбиваємо» Primary під час запису, читання з Secondary.
2. **Транзакції**: неузгоджений стан без транзакції, відкат у транзакції, `WriteConflict`.
3. **Шардований кластер** (2 шарди × 3 вузли + 3 config servers + `mongos`): поганий, хороший і складений shard key.

Усе запускається через `./demo.sh`, і **номер команди — це номер кроку заняття**:
`./demo.sh 1.2` — частина 1, крок 2. `./demo.sh` без аргументів друкує повний список.
Кожна команда спершу показує справжню команду `docker` (рядок з `$`), а потім виконує її —
те саме можна набрати руками.

Цифри нижче — з реального прогону. У вас вони будуть трохи іншими: час, ім'я Primary, відсотки.

## Що потрібно

- Docker + Docker Compose. Пам'ять: replica set — близько 0.3 ГБ, шардований кластер — близько 1.6 ГБ.
- Windows: запускайте `./demo.sh` з Git Bash або WSL.
- Порти на хост не відкриваються: усе працює через `docker exec`.

> MongoDB 8.x не стартує на Linux з ядром 6.19+ (SERVER-121912), тому використовується 7.0.

## Шпаргалка

| Команда | Що робить |
| --- | --- |
| `./demo.sh up` | replica set для частин 1–2 (~15 с) |
| `./demo.sh up shard` | шардований кластер для частини 3 (~20 с) |
| `./demo.sh 1.1` … `3.4` | кроки заняття |
| `./demo.sh kill` / `revive` | «вбити» Primary / повернути вузол |
| `./demo.sh shell [mongo2\|mongos]` | інтерактивний `mongosh` |
| `./demo.sh down` | зупинити все й видалити дані |

Скрипти лежать у `scripts/` і названі за кроками: `1_2_write_concern.js` — це крок 1.2.
Усі кроки можна запускати повторно.

## Частина 1. Replica set і відмовостійкість

```bash
./demo.sh up
```
```
mongo1:27017 PRIMARY
mongo2:27017 SECONDARY
mongo3:27017 SECONDARY
Зараз Primary: mongo1:27017
Замовлень у test.orders: 0
```

Три вузли однакові. Хто з них Primary, вирішують вибори, тому це **не обов'язково mongo1**.
Четвертий контейнер, `rs-client`, — це клієнт з `mongosh`. Він підключається до **всього**
replica set: `mongodb://mongo1,mongo2,mongo3/?replicaSet=rs0`. Клієнт окремий, бо він не має
падати разом із сервером, який ми будемо «вбивати».

### Ручний режим: `mongosh` до всього replica set

Щоб набирати команди самому, а не скриптами:

```bash
docker exec -it rs-client mongosh 'mongodb://mongo1,mongo2,mongo3/?replicaSet=rs0'
```

Коротка форма — `./demo.sh shell`. Це той самий клієнт і та сама адреса **всього** набору:
`mongosh` сам знаходить Primary і переживає failover, тож сесію можна тримати відкритою під час
`kill`. `-it` потрібен для інтерактивного режиму, адресу беріть в одинарні лапки (у ній є `?`).
Вихід — `exit` або Ctrl+D.

```js
rs.status().members.forEach(m => print(m.name, m.stateStr))   // ролі вузлів
rs.status()                            // повний стан: health, відставання, heartbeat
rs.printSecondaryReplicationInfo()     // на скільки секунд відстає кожен Secondary
rs.conf()                              // конфігурація: priority, votes
use test
db.orders.countDocuments()
load("/scripts/1_1_status.js")         // скрипт кроку; після нього db = test
```

Одна команда без інтерактиву — замість `-it` використайте `--quiet --eval '…'`.

### 1.1 — хто зараз Primary

```bash
./demo.sh 1.1
```

Той самий вивід, що вище. Запускайте цей крок щоразу, коли хочете побачити стан replica set.

### 1.2 — w:1 проти w:"majority"

```bash
./demo.sh 1.2
```
```
w:1 зайняло: 15 мс
w:majority зайняло: 9 мс
20 вставок з {"w":1} → 18 мс
20 вставок з {"w":"majority","j":true} → 33 мс
```

Один замір нічого не показує: перша вставка «прогріває» з'єднання, тому `w:1` тут навіть повільніший.
У серії з 20 вставок **majority приблизно вдвічі довший**: Primary чекає, поки запис підтвердить
ще хоча б один вузол. На одній машині це мілісекунди. Між дата-центрами до кожного запису
додається мережева затримка.

### 1.3 — падіння Primary під час запису

Потрібні два термінали:

```bash
./demo.sh 1.3     # термінал 1: вставка замовлення кожні 300 мс (зупинка — Ctrl+C)
./demo.sh kill    # термінал 2: docker kill поточного Primary
```
```
00:40:58 Вставлено замовлення ORD-118
00:40:59 Вставлено замовлення ORD-119
00:41:10 Вставлено замовлення ORD-120      ← пауза 11 с: вибори нового Primary
00:41:10 Вставлено замовлення ORD-121
```

Помилки немає, є лише пауза. Драйвер чекає на нового Primary, а потім сам повторює запис
(**retryable writes**). Для застосунку failover виглядає як коротке «зависання». Близько 10 с — це
`electionTimeoutMillis`: стільки Secondary чекають, перш ніж вирішити, що Primary мертвий.

Що сталося з replica set і як повернути вузол:

```bash
./demo.sh 1.1       # хто тепер Primary
./demo.sh revive    # повернути вбитий вузол
```
```
mongo1:27017 SECONDARY
mongo2:27017 (not reachable/healthy)
mongo3:27017 PRIMARY
```

Після `revive` вузол **не стає знову Primary**: він доганяє зміни з oplog і працює як Secondary.

Спробуйте також `./demo.sh kill stop` (коректна зупинка замість раптової): паузи не буде зовсім.
Primary встигає сам передати роль іншому вузлу.

### 1.4 — читання з Secondary

```bash
./demo.sh 1.4      # скрипт сам знаходить Secondary і підключається напряму до нього
```
```
А. Пряме підключення до mongo1:27017 | isWritablePrimary: false
   читання → прочитано документів: 3
   запис   → помилка: NotWritablePrimary
Б. Підключення до всього replica set — хто відповідає на find():
   за замовчуванням (primary)           → mongo3
   .readPref('secondaryPreferred')      → mongo2
   після conn.setReadPref('secondary')  → mongo2
```

- **А.** Писати на Secondary не можна ніколи. Читати при прямому підключенні `mongosh` дозволяє.
- **Б.** Read preference має сенс, коли клієнт бачить увесь replica set: тоді він вирішує,
  на який вузол відправити запит.

Читання з Secondary може повернути трохи застарілі дані (replication lag). Воно підходить для
звітів та аналітики і не підходить для «прочитати щойно записане».

### Бонус: `./demo.sh 1.3 raw` — failover без автоматичного повтору

Та сама вставка, але з `retryWrites=false`. Запустіть і зробіть `./demo.sh kill` у другому терміналі:

```
00:41:39 Вставлено замовлення ORD-113
00:41:42 ❌ ПОМИЛКА: getaddrinfo ENOTFOUND mongo3
00:41:45 ❌ ПОМИЛКА: getaddrinfo ENOTFOUND mongo3
00:41:48 ❌ ПОМИЛКА: getaddrinfo ENOTFOUND mongo3
00:41:50 Вставлено замовлення ORD-114
```

Саме це бачив би застосунок, якби драйвер не повторював запис сам.

### Бонус: `./demo.sh rollback` — підтверджений запис зникає

Скрипт за ~35 с проходить п'ять кроків і підписує кожен:

1. Відрізає Primary від мережі (`docker network disconnect`).
2. Записує в нього 5 замовлень з `w:1`. Вузол їх **підтверджує**: він ще вважає себе Primary.
3. Два інші вузли обирають нового Primary. Цих 5 замовлень на ньому немає.
4. Повертає мережу. Старий Primary бачить, що його історія розійшлася, і відкочує свої записи.
5. Показує файл із відкоченими документами.

```
/data/db/rollback/c7be6141-…/removed.2026-11-17T00-42-48.0.bson
{"_id":{"$oid":"6afba2f9…"},"orderId":"ROLLBACK-1"}
…
Замовлень ROLLBACK-* у кластері: 0
```

Клієнт отримав «ОК» на 5 замовлень, а в базі їх немає. З `w:"majority"` такого не буває:
запис підтверджується лише тоді, коли він уже є на більшості вузлів.

## Частина 2. Транзакції

Працюємо на тому самому replica set, база `shop`. Сценарій: купуємо 5 віджетів. Це дві операції:
списати товар зі складу (`inventory`) і створити замовлення (`orders`).

### 2.1 — дані складу

```bash
./demo.sh 2.1
```
```
Початковий стан складу:
   {"sku":"WIDGET-500","quantity":10,"reserved":0}
   {"sku":"GADGET-100","quantity":3,"reserved":0}
```

Кроки 2.2–2.4 самі повертають склад до цього стану, тому їх можна запускати в будь-якому порядку.

### 2.2 — без транзакції

```bash
./demo.sh 2.2
```
```
💥 Сервер впав у найневідповідніший момент!
Склад:     {"sku":"WIDGET-500","quantity":5,"reserved":5}
Замовлень: 0  ← товар списано, а замовлення немає
```

Збій стався між двома операціями. Перша вже записана, другої не було. Це **неузгоджений стан**.

### 2.3 — те саме в транзакції

```bash
./demo.sh 2.3
```
```
── Спроба 1: збій усередині транзакції ──
Поточний залишок: 10
Після списання: усередині транзакції залишок 5 | поза транзакцією 10
🔄 Транзакція відкотилася: Все ще падаємо, але результат буде іншим
Склад:     {"sku":"WIDGET-500","quantity":10,"reserved":0}
Замовлень: 0

── Спроба 2: без збою ──
Поточний залишок: 10
Після списання: усередині транзакції залишок 5 | поза транзакцією 10
✅ Замовлення створено!
Склад:     {"sku":"WIDGET-500","quantity":5,"reserved":5}
Замовлень: 1
```

Функція `buyWidgets` у скрипті одна, різниця між спробами — один рядок `throw`.
Зверніть увагу на рядок «усередині 5 | поза транзакцією 10»: поки транзакція не завершена,
її змін ніхто інший не бачить. Результат — **усе або нічого**.

### 2.4 — WriteConflict: двоє купують останній товар

```bash
./demo.sh 2.4
```
```
A: бачить залишок 3
A: купив 3 шт., але commit ще не зробив
B: бачить залишок 3 (змін A ще не видно)
B: помилка WriteConflict | мітки: ["TransientTransactionError"]
A: commit
Склад: {"sku":"GADGET-100","quantity":0,"reserved":0}  ← 0, а не -3
```

Обидва покупці бачили 3 штуки. Без захисту залишок став би −3. MongoDB дозволяє змінити документ
лише першій транзакції, друга одразу отримує `WriteConflict`. Мітка `TransientTransactionError`
означає «повторіть транзакцію». `withTransaction()` з кроку 2.3 робить цей повтор сам.

## Частина 3. Шардування

```bash
./demo.sh up shard
```
```
Шард shard1 → shard1/node11:27018,node12:27018,node13:27018
Шард shard2 → shard2/node21:27018,node22:27018,node23:27018
```

Загальна схема кластера:

```
                       клієнт (mongosh / застосунок)
                                     │
                                     ▼
                                  mongos  ── маршрутизатор, даних не зберігає
                                     │
            ┌────────────────────────┼────────────────────────┐
            ▼ карта chunks           ▼ дані                   ▼ дані
┌──────────────────────┐ ┌──────────────────────┐ ┌──────────────────────┐
│ config servers       │ │ shard1               │ │ shard2               │
│ replica set "cfg"    │ │ replica set "shard1" │ │ replica set "shard2" │
│ cfg1  cfg2  cfg3     │ │ node11 node12 node13 │ │ node21 node22 node23 │
│ порт 27019           │ │ порт 27018           │ │ порт 27018           │
└──────────────────────┘ └──────────────────────┘ └──────────────────────┘
```

- **mongos** — маршрутизатор. Клієнти підключаються тільки до нього, даних він не зберігає.
  Куди відправити запит, дізнається з «карти» config servers і тримає її в кеші.
- **cfg1–cfg3** — config servers (`mongod --configsvr`). Зберігають метадані: які є шарди і який
  діапазон ключа (chunk) лежить на якому шарді. Даних застосунку тут немає. Три вузли, бо без
  «карти» кластер не знає, де дані.
- **shard1, shard2** — тут дані (`mongod --shardsvr`). Кожен шард — replica set з трьох вузлів:
  усередині свій Primary і свій failover, як у частині 1. Ім'я вузла читається як «шард, вузол»:
  `node12` — шард 1, вузол 2.

Разом 10 контейнерів: 9 `mongod` у трьох replica set і один `mongos`. `up shard` ініціює три
набори (`rs.initiate`) і реєструє шарди (`sh.addShard`) — лише після цього вони стають одним кластером.

Усі три кроки вставляють дані й показують, як вони розійшлися по шардах.

### Ручний режим: `mongosh` до кластера через `mongos`

```bash
docker exec -it mongos mongosh
```

Коротка форма — `./demo.sh shell mongos`. До шардованого кластера підключаються **тільки через
`mongos`**, як до звичайного сервера: він сам маршрутизує запити на потрібні шарди. Адреса не
потрібна — `mongos` слухає стандартний порт 27017 у своєму контейнері.

```js
sh.status()                            // повний звіт: шарди, бази, chunks (кілька екранів)
db.adminCommand({ listShards: 1 })     // склад кластера
sh.getBalancerState()
use store
db.events_good.getShardDistribution()  // документи й розмір по шардах
load("/scripts/3_0_show.js"); showDistribution("events_good")   // смужки, як у кроках 3.1–3.3
```

Зазирнути всередину шарда (ролі його вузлів) — напряму до вузла, з нестандартним портом:
`docker exec -it node11 mongosh --port 27018` (шарди), `docker exec -it cfg1 mongosh --port 27019`
(config servers). Писати дані так не можна: запис в обхід `mongos` ламає облік chunks.

### 3.1 — поганий ключ: `{ createdAt: 1 }`

```bash
./demo.sh 3.1
```
```
store.events_bad
  shard1 █████████████████████████  10000 док. 100% | chunks: 1
  shard2 ·························      0 док.   0% | chunks: 0
```

Час лише зростає, тому кожен новий документ потрапляє в «останній» chunk. Усі записи йдуть
на один шард — це **write hotspot**. Серверів два, працює один.

### 3.2 — хороший ключ: `{ _id: "hashed" }`

```bash
./demo.sh 3.2
```
```
store.events_good
  shard1 █████████████············   5052 док.  51% | chunks: 2
  shard2 ████████████·············   4948 док.  49% | chunks: 2
```

Хеш розкидає сусідні значення по всьому діапазону, записи діляться приблизно порівну.
Ціна: запит за діапазоном дат тепер іде на всі шарди.

### 3.3 — складений ключ: `{ userId: 1, _id: "hashed" }`

```bash
./demo.sh 3.3      # 100 000 подій для 100 користувачів
```
```
userId < user_50 → shard1 | userId >= user_50 → shard2
store.user_events
  shard1 ████████████·············  46268 док.  46% | chunks: 1
  shard2 ██████████████···········  53732 док.  54% | chunks: 1
find({ userId: "user_42" }) → SINGLE_SHARD шарди: shard1   ← є префікс ключа
find({ page: "/page/42" })  → SHARD_MERGE  шарди: shard1, shard2   ← ключа в запиті немає
```

Запит з `userId` mongos відправляє на один шард (**targeted query**). Запит без ключа він
розсилає на всі шарди й зливає результати (**scatter-gather**).

Важливо: на порожній колекції такий ключ дає **один** chunk. Balancer ділить chunk лише тоді,
коли даних більше за його розмір (128 МБ), а тут ~9 МБ. Тому скрипт сам ділить діапазон навпіл
(`sh.splitAt` + `moveRange`). На великих обсягах це зробив би balancer.

### 3.4 — діагностика кластера

```bash
./demo.sh 3.4
```
```
Шард shard1 → shard1/node11:27018,node12:27018,node13:27018
Шард shard2 → shard2/node21:27018,node22:27018,node23:27018
Balancer увімкнено: true
chunks events_good, фільтр за ns:    []  ← порожньо: з MongoDB 5.0 поля ns немає
chunks events_good, фільтр за uuid: [{"_id":"shard1","count":2},{"_id":"shard2","count":2}]
```

Далі скрипт друкує всі три колекції поруч. Повний звіт — `./demo.sh shell mongos`, потім `sh.status()`.

Колекція `config.chunks` з MongoDB 5.0 не має поля `ns`: chunks прив'язані до **UUID колекції**,
який береться з `config.collections`.

```bash
./demo.sh down
```

## Що забрати із заняття

1. Replica set переживає падіння Primary сам: близько 10 с виборів, які драйвер ховає за паузою.
2. `w:1` швидший, але підтверджений запис може зникнути при rollback. `w:"majority"` повільніший і такого не допускає.
3. Читання з Secondary розвантажує Primary ціною можливо застарілих даних.
4. Кілька пов'язаних змін без транзакції при збої лишають неузгоджений стан. Транзакція застосовує всі або жодну.
5. `WriteConflict` — нормальна поведінка конкурентних транзакцій. Застосунок має повторити транзакцію.
6. Shard key визначає, куди йдуть записи й запити. Монотонний ключ дає hotspot, hashed — рівний розподіл, складений — targeted-запити за префіксом.
7. Змінити shard key можна (`reshardCollection` з 5.0), але це переписування всієї колекції. Обирайте ключ одразу.
